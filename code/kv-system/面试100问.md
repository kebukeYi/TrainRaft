# 分布式 KV 项目 · 面试 100 问

> 全部问题与答案基于本项目（基于 etcd raft 库的三节点强一致 KV，C++17 / brpc / RocksDB / ZooKeeper）的**真实实现与实测数据**。
> 难度分四档：A 入门（1–18）、B 进阶（19–45）、C 工程实践（46–75）、D 专家与开放（76–100）。
> 用法：先按档位自测，答不上来的直接看答案，再去代码里核对。

## A 档 · 项目与基础（1–18）

**1. 用一句话介绍这个项目。**
基于 Raft 共识实现的三节点分布式强一致 KV 存储，支持强一致、线性一致读（ReadIndex）与弱一致三种读模式，含 WAL 持久化、快照与崩溃恢复；客户端通过 brpc 访问，leader 通过 ZooKeeper 注册发现。

**2. 它"分布式"体现在哪？**
数据在 3 个节点各存一份完整副本（每节点一个 RocksDB），写请求经 Raft 达成多数派后在各节点按相同日志序列重放，因此任何一个节点宕机（少数派）不影响可用性与一致性。

**3. 集群里 leader 怎么确定？ZooKeeper 里存的是什么？**
Raft 自己选主；选出来后 leader 把节点地址列表（形如 `127.0.0.1:63791 127.0.0.1:63792 ...`）写到 ZK 的 `/raft` 节点。客户端/压测工具读这个列表做服务发现，**约定列表第 1 个是 leader**，其余是 follower。所以 ZK 只承担"注册表"，不参与一致性。

**4. `Node / NodeImpl / RaftNode / RaftNodeImpl / Raft` 各自干什么？为什么不能合成一个类？**
分层是为了"让纯算法和工程管道解耦"：
- `Raft`：纯状态机内核，只管选举、日志复制、commit 推进等算法决策，不碰 IO。
- `Node/NodeImpl`：包装 `Raft`，对外提供 `Propose / ReadIndex / GetReady / Advance / Tick`，负责把算法产出的"待办"打包成 Ready。
- `RaftNode/RaftNodeImpl`：工程管道——把 Ready 落成 WAL、发消息、应用状态机、触发快照，并管理 io_service / 定时器 / 状态机生命周期。
- 上层 `ClientServiceImpl` 只面对 `RaftNode` 接口，不感知 raft 内部。

**5. 为什么不让所有代码写在一个类里？**
三个理由：① `Raft` 是从 etcd 移植的纯算法，独立才能在测试里脱离网络单测；② IO 与算法耦合后，任何 IO 抖动都会污染选举时序；③ 分层后可替换（比如把 `MemoryStorage` 换成磁盘存储、把 brpc 换成 gRPC）而不动算法。

**6. 一次写请求的完整链路？**
`ClientService.Set` → 构造 `RaftEntryData` 并登记到 `pendingRequests_` → `RaftNodeImpl::ProcessProposal` 攒批 → raft 线程 `FlushProposals` 批量 `Propose` → Leader 追加本地日志并广播 `MsgApp` → 多数派落盘回复 → commit 推进 → `GetReady` 带出 committedEntries → 写 WAL（一次 fsync）→ `ApplyStateMachine` 写到 RocksDB → 只有**发起节点**通过 `done->Run()` 回包。

**7. 一次读请求的链路？三种模式差别在哪？**
三种都从 `ClientServiceImpl::Get` 进入，按 `KV_READ_MODE` 分叉：
- **弱读 weak**：不经共识，直接把请求包成 Entry 交给状态机读本地 RocksDB 并回包（可能读到旧数据）。
- **线性一致读 readindex**：先向 leader 要一个安全水位（commit index），等本地 `appliedIndex_ >= readIndex` 后再读。
- **强一致读 strong**：走 `ProcessProposal`，把读也当作一条日志走完整共识流程。

**8. 启动流程讲一下。**
`Main` 解析 `--id/--configFile` → 注册 SIGTERM 处理 → `RaftNodeImpl` 构造：建目录 → `ReplayWAL`（先加载快照，再选择性重放 WAL）→ 填 `Config`（electionTick/heartbeatTick/preVote/readOnlyOption 等）→ 建 `MemoryStorage`/`Node`/`Transport`/`StateMachine` → 启动状态机工作线程与 io_service → `StartTimer` 驱动 tick → 通过 ZK 注册并在选出 leader 后写 `/raft`。

**9. 什么是 Ready 机制？为什么需要它？**
`Raft` 是纯计算内核，不能自己做 IO。它把"需要落盘/发送/应用"的东西攒起来，上层用 `GetReady()` 一次性取走，处理完再 `Advance()` 告知。这样内核保持无副作用、可确定性重放，工程侧则能按自己的节奏批量处理（我们正是借此做组提交：一批提案只 fsync 一次）。

**10. `GetReady` 打包了哪些东西？**
`hardState`（term/vote/commit）、`entries`（待持久化的新日志）、`committedEntries`（待应用到状态机）、`messages`（待发送消息）、`readStates`（读结果）、`snapshot`（待持久化的快照）。

**11. `Advance` 做什么？不调用会怎样？**
把 `applied` 水位、unstable 日志、已发送消息等状态推进到"已处理"位置。不调用的话内核认为你还没处理完，`GetReady` 会一直返回同一批内容，系统停摆。

**12. 为什么日志分成 `storage_`（MemoryStorage）和 `unstable_`？**
`storage_` 存"已经持久化、不会再变"的日志（可直接压缩/取快照）；`unstable_` 存"刚追加、还没落盘"的日志。分开后内核在 `unstable_` 里找最新日志、在 `storage_` 里做历史匹配，边界清晰；快照压缩时也只需处理 `storage_`。

**13. `applied <= committed` 这个不变式为什么重要？**
committed 表示"多数派已确认、不会再回滚"，applied 表示"已经写进状态机/对外可见"。若 applied 跑到 committed 前面，就可能对外暴露一条未来会被覆盖的日志——这是违反线性一致性的数据错误，所以 ReadIndex 才会在 `appliedIndex_ < readIndex` 时**拒绝读**而不是硬读。

**14. 什么是 term？为什么需要它？**
单调递增的任期号，是"逻辑时钟"。它让节点能识别过期消息（term 小的直接拒绝）、避免脑裂（一个 term 最多一个 leader）、并作为日志比较的第二关键字。

**15. `MsgHup / MsgProp / MsgReadIndex` 分别是什么？**
`MsgHup`：本地触发的"我要竞选"，follower 收到自己超时后进入 Candidate；`MsgProp`：客户端提案消息，把要写的 Entry 塞进 raft；`MsgReadIndex`：读请求发给 leader 要安全水位（follower 收到会转发给 leader）。

**16. 选举过程？**
follower 超过随机选举超时（`[electionTick, 2*electionTick-1]` 个 tick）没收到 leader 消息 → 转 PreCandidate 发 `MsgPreVote` → 拿到多数派后转 Candidate、term+1、投自己并发 `MsgVote` → 拿到多数派成为 leader，立刻广播心跳确立权威。

**17. 日志复制过程？日志匹配性质是什么？**
leader 为每个 follower 维护 `nextIndex/matchIndex`，发 `MsgApp` 时带上**前一条日志的 (index, term)**；follower 校验不上就拒绝（`MsgAppResp` reject），leader 递减 `nextIndex` 重试直到对齐。日志匹配性质：两份日志若在某 index 的 term 相同，则该 index 之前的所有日志完全相同。

**18. commit 是怎么推进的？为什么 leader 只能提交当前 term 的日志？**
leader 收到多数派确认后，取"多数派 matchIndex 的中位数"作为可提交位置。但**只能提交自己当前 term 的日志**（即使旧 term 日志已被多数派复制）——否则会出现"已提交日志被覆盖"的经典反例（Figure 8）。旧 term 日志要靠提交一条当前 term 的新日志来"顺带"提交。

## B 档 · Raft 机制与存储（19–45）

**19. 预投票（preVote）解决什么问题？**
防止"分区节点捣乱"：一个与集群隔离的节点不断超时、term 一路自增；等网络恢复时它的高 term 会把健康的 leader 逼下台。preVote 要求先"试探性拉票"，只有能拿到多数派才真正加 term，从而避免无谓的选主风暴。

**20. `checkQuorum` 干什么？**
leader 周期性检查"我是否还得到多数派响应"；不满足就主动退位。避免一个被隔离的 leader 一直对外提供（可能是过期的）读服务。

**21. leader 转移（leadership transfer）怎么做？为什么有用？**
让当前 leader 把权威平滑交给指定节点（先让它追平日志、再发 `MsgTimeoutNow` 催它竞选）。用于滚动升级、机架亲和、负载均衡，能避免"停掉 leader 后等选举超时"带来的抖动。

**22. ReadIndex 读的完整流程？**
① follower 收到读请求先把 `MsgReadIndex` 转给 leader（我们已经知道的话）；② leader 记录当前 commit index 作为 readIndex，同时**发起一轮心跳确认自己仍是 leader**；③ 多数派确认后把 readIndex 放进 `readStates_`；④ 读发起方取到 readIndex，等本地 `appliedIndex_ >= readIndex` 才读本地状态机。

**23. `readStates` 是什么？谁消费？**
内核输出的"读结果"队列，元素是 `{index, requestCtx}`。`RaftNodeImpl::PullReadyEvents` 把它取出来交给 `PublishReadStates`，由其判断水位是否跟上，够就执行读、不够就回一个拒绝（`EntryWarningReadIndex`）。

**24. `appliedIndex < readIndex` 为什么要拒绝读？**
说明本节点状态机还没追上"多数派已确认"的水位，此时读会读到旧值。宁可返回错误也不能返回过期数据；上层可以重试，重试时水位通常已经追上。

**25. lease-based read 和 ReadIndex 怎么选？**
lease 模式下 leader 在租约期内假定自己仍是 leader，读可以**不发那轮心跳确认**，延迟更低；代价是依赖时钟（要保证租约时间小于选举超时）。本项目通过 `KV_READ_ONLY_OPTION=lease` 可切，默认走 `ReadOnlySafe`（更保守、不依赖时钟）。

**26. 强一致读为什么"等于一次写"？实测数据？**
因为实现上 `strong` 直接走 `ProcessProposal`，读也被当成一条日志：提案 → 复制 → 多数派落盘 → 提交 → 应用 → 回包，和写完全同一条路。实测 32 线程不限速下强一致读 309 QPS / p50 81.9ms，写 312 QPS / p50 85.7ms，基本重合。

**27. 弱读的实现和风险？**
把读请求包成 `EntryNormal` 直接交给本地状态机读 RocksDB，不经过任何共识。风险是可能读到落后数据（stale read），甚至读到已被新 leader 覆盖前的旧值；只适用于"能容忍旧数据"的场景。

**28. 三种读模式的实测结论？**
同并发下：**弱读 ≈ 线性一致读**（leader 上 ReadIndex 的额外往返是本地往返，几乎免费），**强一致读 ≈ 写**。非共识路径（weak/readindex）比共识路径（strong/write）吞吐高 **4~6 倍**、p50 低约 **7 倍**。例如 32 线程：weak 1979 QPS / p50 11.7ms，strong 309 QPS / p50 81.9ms。

**29. WAL 文件格式？为什么每条记录带 crc32？**
格式 `[type(1B)][crc32(4B)][len(3B)][data]`，文件名 `%016llx-%016llx.wal`（起止 index）。带 crc32 是为了**检测崩溃时写了一半的尾部记录**：重启扫描时校验失败就认为该记录及之后都无效，从而截断到最后一个完整记录。

**30. 为什么每条写都要 fsync？不 fsync 会怎样？**
`fwrite` 只写到用户态缓冲，进程崩溃（SIGKILL/掉电）时数据会丢。`fflush + fsync(fileno)` 才能真正落盘。不 fsync 的话，已回复客户端的写可能在崩溃后消失，破坏 Raft 的持久性保证。

**31. 重启怎么恢复？`ReplayWAL` 做了什么？**
① 加载快照拿到 `snapshotIndex/term/confstate`；② 从快照 index 之后选择性重放 WAL 中的日志，重建 `MemoryStorage` 与硬状态（term/vote/commit）；③ 把快照 index 写入内存日志存储作为起点；④ 用重放出的 `appliedIndex` 让状态机追平。

**32. 有快照时快照和 WAL 怎么衔接？**
快照覆盖了 `<= snapshotIndex` 的所有状态，所以 WAL 中这部分日志无需重放（会被跳过），只重放 `> snapshotIndex` 的部分。这既加速恢复也支持日志压缩。

**33. 快照什么时候触发？**
每应用 `snapCount_` 条日志检查一次是否到达阈值（可配置），到达就异步生成快照并清理旧 WAL。

**34. 快照文件格式？`SaveSnap` 曾经的 bug 是什么？**
文件 `<term>-<index>.snap`，内容 `[dataLen][crc32][data]`。曾经的 bug：先 `make_shared<SnapshotRecord>()` 只分配了 8 字节（长度头），却直接 `memcpy` 整个 payload 进去，ASan 报 `heap-buffer-overflow`。修法是**先写 8 字节长度头、再单独写 data**，不再借用那个只够放头的小对象。

**35. `CreateSnapshot` 里 `set_allocated_confstate` 的问题？**
`set_allocated_*` 会把裸指针的所有权交给 protobuf 对象；如果原对象由 `shared_ptr` 管理，就会**双重释放**（shared_ptr 和 protobuf 都去 delete）。改成 `mutable_confstate()->CopyFrom(*cs)` 只做拷贝，所有权清晰。

**36. 快照安装（InstallSnapshot）流程？**
leader 发现某 follower 需要的日志已被压缩掉（`nextIndex <= snapshotIndex`）时，直接发送快照；follower 收到后清空本地日志、用快照重置状态机与 `appliedIndex`，再回复 leader 继续增量复制。

**37. `ConfState` 是什么？为什么快照要带上？**
它是"当时的集群成员 id 列表"。快照一旦生成，历史日志可能被删掉，成员变更的历史也就没了，所以必须把成员配置随快照一起保存，重启/安装快照后才能知道集群有谁。

**38. 快照为什么要异步生成？曾经踩了什么坑？**
全表遍历（`db_->Get(kvData)` 扫整个 RocksDB）很慢，不能阻塞 raft 线程，所以投递到状态机自己的 io_service 上跑，用 `std::promise/future` 取回结果。坑：`ioService_.run()` 在没有任务时会**立即返回**导致工作线程退出，之后 `future.wait()` 永久阻塞（死锁）。修法是给 io_service 加 `boost::asio::io_service::work` 保活。

**39. 日志压缩和快照的关系？**
快照就是压缩的产物：把"截至某 index 的全部状态"物化成一份数据，之后 `<= 该 index` 的日志即可丢弃。没有压缩，日志会无限增长、重启恢复越来越慢。

**40. `MemoryStorage` 的作用？重启后它的内容从哪来？**
给 raft 内核提供"可读的已持久化日志"，让内核做日志匹配/取日志。重启后不是从磁盘逐条读，而是由 `ReplayWAL` 重放 WAL（起点是快照 index）重建出内存里的日志视图。

**41. unstable 日志什么时候落盘？**
上层处理 `Ready` 时把 `entries` 写入 WAL 并 fsync，成功后 `Advance` 把它们从 `unstable_` 移到 `storage_`。

**42. `nextIndex / matchIndex` 的作用？**
`nextIndex` 是"下一次要发给该 follower 的日志起点"，`matchIndex` 是"已确认与该 follower 匹配到的最高 index"。leader 用 `matchIndex` 的多数派中位数算 commit；用 `nextIndex` 决定每次发什么、失败就回退重试。

**43. 为什么 `MsgApp` 要带前一条日志的 (index, term)？**
这是"日志匹配检查"的依据：只有 follower 在 `index` 处的 term 与之一致，才说明两者此前日志完全相同，才能安全追加。这是 Raft 正确性的核心不变量。

**44. 单节点 / 双节点集群有什么问题？**
单节点：多数派就是自己，退化成"本地写 + WAL"，没有容错。双节点：多数派是 2，挂一个就失去多数派、完全不可写，可用性反而比单节点差——所以生产上通常用 3/5 个节点。

**45. 网络分区下的行为？**
少数派分区：无法凑齐多数派，既不选主也不提交，对外不可写（保证安全）。多数派分区：选出新 leader 继续服务。旧 leader 靠 `checkQuorum` 或收到更高 term 消息后下台；恢复连通后，旧 leader 的未提交日志被新 leader 覆盖（日志匹配性质保证这一点）。

## C 档 · 工程实现与并发（46–75）

**46. `pendingRequests_` 的 data race 是怎么发现的？**
压测时随机 segfault。用 **ASan**（`-fsanitize=address`）重跑，报 `heap-use-after-free`：brpc 工作线程在插入登记，raft 线程同时 `find/erase`，`unordered_map` 无任何保护。

**47. 怎么修的？为什么封装成 `AddPendingRequest / TakePendingRequest` 而不是到处加锁？**
加了 `pendingMutex_`，并把"写入登记"和"取走登记"分别封装成两个方法，内部统一加锁。好处：① 锁的粒度与容器操作绑定，不可能漏；② "取走即删除"的语义集中在一处，避免两处（状态机回包、sweeper 超时）重复回复。

**48. 请求 id 为什么必须原子？非原子会怎样？**
`nextRequestId_++` 在多线程下不是原子操作，两个并发请求可能拿到同一个 id。后果是登记互相覆盖、回包张冠李戴（甚至回复到错误的请求对象上），属于极难复现的数据错乱。改成 `std::atomic<uint32_t>` 自增。

**49. 为什么 Set/Del 要"先登记再提案"？**
回包是靠 requestId 去 `pendingRequests_` 找登记。如果先提案、后登记，日志可能很快被多数派提交并应用，状态机回包时**找不到登记**，客户端就会一直挂着直到超时。所以必须登记在前，并设置好 `replyMeta.type`。

**50. sweeper 线程解决什么问题？为什么需要超时回复？**
请求可能因为 leader 切换、节点过载等原因永远等不到回包；若没人清理，对应 RPC 连接会一直挂着，`done` 永不执行 → 连接不关 → FD 泄漏。sweeper 每 500ms 扫一遍，把超过 `KV_PENDING_TIMEOUT_MS`（默认 10s）的登记摘出来，在锁外调用 `done->Run()` 返回错误，让客户端尽快失败重试。

**51. FD 泄漏（CLOSE_WAIT）的根因？怎么定位和修复？**
现象：leader 日志报 `Fail to create socket: Too many open files [24]`，`ls /proc/<pid>/fd | wc -l` 达 8800+，其中 CLOSE_WAIT 连接 7669 个。根因就是上一条——pending 请求的 `done` 永不执行，brpc 侧连接无法关闭。修复后 leader FD 从 8800 降到 **26**，CLOSE_WAIT 归零。

**52. 为什么 leader 会积累这么多 FD？**
所有客户端连接都集中在 leader（写和 ReadIndex 都要找 leader），泄漏速率被放大；`ulimit -n` 默认 1024，很快就 EMFILE。这也是压测脚本里要 `ulimit -n 65535` 的原因。

**53. `Send` 的内存泄漏在哪？brpc 异步回调的对象所有权怎么管？**
原来 `Send` 里 `new` 出来的 `controller/request/response` 在发送后没人释放。brpc 的异步调用需要这些对象活到回调触发，所以改成自定义 `SendDone : google::protobuf::Closure`，由回调持有它们，`Run()` 里发完日志后统一 delete，最后 `delete this`。

**54. 为什么把 `Send` 改成异步？同步有什么后果？**
同步发送时，只要某个 follower 卡住（网络不通/进程冻结），raft 线程就会阻塞在 send 上，**整个集群停止推进**（连心跳都发不出去）。实测：人为冻结一个 follower，同步版 6 秒只发出 14 条、0 成功；异步版发出 2727 条、0 错误。

**55. 异步后怎么保证生命周期安全？**
关键是"回调拥有对象"：把所有需要在回调里用到的对象交给 `SendDone` 持有（`shared_ptr<Channel>` + 裸指针由回调负责 delete），回调是唯一释放点；同时 `Send` 内部对 channel 查表加锁，避免 channel 被并发替换时悬空。

**56. Group Commit 怎么实现的？`flushScheduled_` 起什么作用？**
`ProcessProposal` 在**非 raft 线程**时先把提案塞进 `pendingProposals_`，并且只 post 一个 flush 任务（`flushScheduled_` 为 true 时不重复排）。raft 线程执行 `FlushProposals`：锁内 swap 出整批、把标志复位，锁外逐条 `Propose`，最后只调用**一次** `PullReadyEvents`。

**57. 为什么组提交能把写吞吐提 20 倍？**
瓶颈是 fsync 的**次数**而不是字节数：每条日志单独走一轮"复制 + fsync"时，吞吐被 fsync 往返锁死（约 25 QPS）。合并后一批 N 条只付出一次 fsync 和一轮复制，吞吐提升到约 **500 QPS**（约 20 倍）。

**58. 组提交会不会增加延迟？怎么权衡？**
会引入"等批"的延迟（最后一条要等同批一起提交），但换来的吞吐提升远大于这点延迟，且批次由 event loop 的一次迭代自然限界（不会无限等）。如果场景极度延迟敏感，可以给批设一个"最多等 X 微秒"的上限。

**59. 为什么 ProcessX 里要区分"是不是 raft 线程"？**
如果在 raft 线程上还去 post 一个任务，会形成"自己等自己"的多余一轮事件循环；直接调用则省一次派发。更关键的是一致性：`FlushProposals / PullReadyEvents` 里有 `assert(pthreadId_ == pthread_self())`，必须在 raft 线程执行。

**60. SIGTERM 处理做了什么？为什么必须做？**
注册 SIGTERM 处理器，收到后走优雅退出路径（而不是被默认动作直接杀死），保证退出前把缓冲的 WAL 数据 fsync 落盘。不做的话，`docker stop` / `kill` 会丢 WAL 尾部。

**61. WAL fsync 和 SIGTERM 为什么必须配合？**
只有 fsync 没有优雅退出，进程被杀时 `fwrite` 缓冲里的数据仍会丢；只有优雅退出没有 fsync，退出时数据仍在用户态缓冲。两者都做，重启后的 commit 才落在 WAL 覆盖范围内。

**62. `LoadState` 为什么要 clamp 而不是 FATAL？**
曾经现象：进程被强杀后重启直接 `LOG_FATAL: state.commit out of range [7515, 7515]`（提交点比最后一条日志还大，因为 WAL 尾部丢了）。这是**可自愈**的：把 commit 钳制到 `[committed_, LastIndex()]` 并打 WARN 即可继续启动，比直接崩掉服务合理得多。修复后重启从 FATAL 变成 3 条 warn 后正常恢复。

**63. 状态机复制那个 bug 是什么？**
原实现只在"发起请求的节点"上执行状态机（`nodeid` 不匹配就直接 return），导致 follower 的 RocksDB 根本没写入；更糟的是回包逻辑也没区分节点，出现跨节点读不一致。

**64. 怎么区分"要不要执行"和"要不要回包"？**
执行：**所有**节点都要执行（否则副本数据不一致，Raft 的前提就是相同日志序列 → 相同状态）。回包：只有 `entryData.nodeid() == raft_->NodeId()`（`is_origin`）的节点才能回包，因为只有它本地有 `pendingRequests_` 登记。

**65. `nodeid` / `requestid` 各自的作用？**
`nodeid` 标识"这个请求是哪个节点接到的"，用于过滤回包方；`requestid` 是全局唯一序号，用于在 `pendingRequests_` 里精确找到当初那个 RPC 并回包。

**66. 快照的 heap-buffer-overflow 是怎么发生的？（复述第 34 题的技术本质）**
`SnapshotRecord` 对象本身只有 8 字节（长度字段），代码却把它当成"足够大的缓冲区"去 `memcpy` 整个 payload，越界写。本质是**用错对象的容量假设**——把"长度头对象"当成"数据缓冲区"。

**67. 为什么 io_service 必须加 work guard？**
`io_service::run()` 在无任务时会立刻返回。状态机工作线程用它跑事件循环，一旦 run 返回线程就退出了，后续投递的任务再也不会被执行（`future.wait()` 死锁）。`io_service::work` 让 run 永不因无任务而退出。

**68. brpc 服务 `Start()` 返回值没检查有什么风险？**
端口被占用/权限不足时 `Start()` 返回失败，但代码忽略返回值继续跑。表现是"进程活着、日志看着正常，客户端全部 Connection refused"，非常难查。应检查返回值并在失败时快速退出或告警。

**69. 每请求打日志对性能有影响吗？实测？**
理论上热路径同步日志会拖慢。实测把每次回包的 `LOG_INFO` 关掉（`KV_LOG_REPLY=0`），弱读 p99 仍是 100.0ms、QPS 2735 vs 2749 —— **在本项目负载下不是瓶颈**。但这不代表可以随便打：高吞吐场景应改为采样或异步日志。

**70. 单线程 raft 事件循环的利弊？**
利：状态机无锁、时序确定、易推理，天然串行化所有共识相关操作。弊：**单点吞吐上限**，任何慢操作（fsync、全表遍历）都会阻塞整个共识推进；扩展只能靠"把非共识工作挪出去"（我们把快照挪到独立 io_service、把发送改异步）。

**71. tick 定时器的作用，改小有什么影响？**
`tick` 推进 raft 逻辑时钟：`heartbeatTick` 个 tick 发一次心跳，`electionTick` 个 tick 触发选举超时；同一回调里还会调 `PullReadyEvents`。改小 tick 会让墙钟上的心跳/选举超时同步变小（除非等比放大时钟数），过小会导致误选主、无谓的唤醒开销。

**72. 那 tick 是性能瓶颈吗？实测怎么说？**
不是。把 tick 从 100ms 改成 10ms（同时把 election/heartbeat 的时钟数放大 10 倍，保持墙钟心跳 100ms、选举超时 1s 不变），弱读和线性一致读的 p90/p99 **完全没有变化**（p99 恒为 100.0ms±0.5ms），启动日志确认参数确实生效。

**73. 状态机为什么挂在 raft 线程上？绕过会怎样？**
挂上去是为了串行化应用顺序。我们做了对照实验（`KV_WEAK_READ_INLINE=1` 让弱读直接在 brpc 工作线程读 RocksDB、不进 raft 线程）：吞吐 298 vs 280 QPS、p99 101 vs 106ms，**没有差别** —— 说明弱读的瓶颈根本不在 raft 线程。

**74. ZooKeeper 挂了会怎样？**
已建立的集群**继续正常工作**（一致性由 Raft 保证，ZK 只做注册表）；受影响的是新客户端/压测工具的服务发现，以及 leader 换届时的重新注册。恢复后 leader 会重新写入 `/raft`。

**75. 为什么用 ZooKeeper 而不是自己实现选主？**
选主已经由 Raft 完成，ZK 在这里只是"放一个地址列表"的公共黑board，客户端一次读取即可；用 ZK 省掉了自己实现"注册中心的可用性/一致性"这一整套问题。代价是引入一个外部依赖——更彻底的方案是让客户端直接连集群、由节点转发，或用 etcd 作为元数据存储。

## D 档 · 性能与排障方法论（76–100）

**76. QPS / p50 / p90 / p99 各是什么？为什么盯 p99？**
QPS 是每秒成功请求数；pXX 表示"XX% 的请求延迟不超过该值"。均值会被少数请求带偏，只描述"平均体验"；**尾延迟**才决定用户实际感受和 SLA（超时、重试、级联失败都发生在尾部）。本项目就出现过 p50 只有 3~4ms 但 p99 卡在 100ms 的情况。

**77. 你们怎么测的？用什么工具、什么参数？**
`rpc_press`（brpc 自带）+ 自研封装脚本。核心参数：`-proto/-method/-server/-input` 描述请求，`-qps` 目标速率（**0 = 不限速**），`-duration` 时长，`-thread_num` 并发度，`-connection_type single/pooled/short`，`-timeout_ms` 超时。脚本从输出里解析 `total_sent/total_error` 和 `[Latency]` 块的 avg/50%/90%/99%/max。

**78. `-qps=0` 是什么意思？什么时候用？**
不限速，尽力打满。用于测**吞吐上限**（容量）；`-qps=N` 定速则用于测**稳态延迟**。两者必须分开看，混在一起会得出错误结论。

**79. 为什么一定要"只打 leader"来测？**
四种场景（写/强读/线性一致读/弱读）打同一个节点，唯一变量才是代码路径本身。如果按 leader 40% / follower 60% 分发，读的差异里就混入了"目标节点不同"的影响，不可比。同时 leader 是所有写和 ReadIndex 的汇聚点，是真正的热点。

**80. 8 个压测线程测出的"容量"为什么是假的？**
因为不限速时 QPS ≈ 并发数 ÷ 平均延迟。8 线程、avg 27ms → 283 QPS，这只是"8 ÷ 0.027"，**与服务器能力无关**。当时却把它当成了服务端上限。

**81. 怎么发现并修正这个错误？**
改测**并发度扫描**：固定不限速，threads 取 4/8/16/32/64/128。结果 QPS 从 106 → 283 → 1044 → 2200 → 2513 → 2905，一路上涨到 ~2800-2900 才平台化——说明真实吞吐平台是 ~2800 QPS，之前那个 240~300 是客户端并发度限制。

**82. Little's Law 在这里怎么用？**
`在途请求数 ≈ QPS × 平均延迟`。它既能解释"为什么 8 线程给不出容量"（在途数被线程数钉死），也能从测得的 QPS 和 avg 反推在途数、验证客户端是否真的打满（我们多次用它确认 threads ≈ QPS×avg，说明客户端已饱和）。

**83. Ping 探针的作用？为什么能排除网络？**
`Ping` 是唯一"直接在 brpc 工作线程上回 pong"的方法，不碰 raft 线程、不碰 RocksDB、不碰 `pendingRequests_`。它跑出 **17262 QPS / p99 2.5ms**，说明 brpc、TCP、容器网络这一层完全没问题——于是所有 Get 的延迟问题只能出在 Get 自己的代码路径上。

**84. ~100ms 尾延迟怎么排查的？排除了什么？**
逐项做对照实验排除：① 定时器（tick 100→10ms，p99 不变）② raft 线程（弱读绕过它，p99 不变）③ 回包日志（关掉，p99 不变）④ 网络底座（Ping 探针，p99 2.5ms）。最后看环境：容器只有 **4 个 CPU** 且与宿主 WSL 共享，却跑着 3 个节点 + 最多 128 压测线程，因此把结论收敛到**容器 CPU 调度**，而不是应用代码。

**85. 为什么"p99 恒为 100.0ms ± 0.5ms"很可疑？**
正常排队形成的尾延迟是连续分布（p90 到 max 之间有平滑过渡）。而 p90≈p99≈max≈100ms 且离散度极小，说明延迟被**量化**到某个固定值附近，通常指向一个周期性事件（定时器/调度片），而不是排队现象。这也是我一开始怀疑 100ms 定时器的原因。

**86. 怎么证明 tick 不是原因？"等比例缩放"的意义？**
如果只把 tick 改成 10ms，墙钟心跳会变成 10ms、选举超时 100ms，集群会频繁误选主，实验不干净。所以把 `electionTick/heartbeatTick` 同时放大 10 倍，**保持墙钟心跳 100ms、选举超时 1s 不变**，只让"回包消费频率"提高 10 倍。结果 p90/p99 纹丝不动 → 定时器不是原因。同时启动日志打印生效参数，确认环境变量真的生效（避免"实验白做"）。

**87. 火焰图 / pprof 怎么用？有什么限制？**
用 gperftools：`LD_PRELOAD=libprofiler.so CPUPROFILE=xxx.prof CPUPROFILE_FREQUENCY=1000` 启动，节点退出时 profile 落盘并打印 `interrupts/evictions/bytes`；再用 `pprof --text/--svg 二进制 prof文件` 出热点。限制：① 只反映 **CPU 时间**，对"阻塞等待"（锁、IO、调度）无能为力——这正是本项目尾延迟的性质；② 本环境 `pprof --text` 走 addr2line 很慢（约 6 分钟/个）；③ 强一致场景因节点长时间饱和，SIGINT 收不干净、profile 没落盘。

**88. CPU 采样数（`interrupts=N`，1kHz）怎么读？**
1kHz 采样下 `interrupts` 约等于"该进程消耗的 CPU 毫秒数"。三节点求和就能横向比较不同场景的 CPU 代价（例如纯读 vs 混合读写）。它衡量的是 CPU 消耗，不是墙钟延迟，别拿它当延迟指标。

**89. ASan 报 `heap-use-after-free` 怎么读？**
输出会给出"谁释放的（free stack）"和"谁在释放后又访问（use stack）"。本项目两条栈分别是 brpc 工作线程插入登记、raft 线程 `find/erase`，于是立刻定位到 `pendingRequests_` 缺少同步。ASan 的价值是**把概率性崩溃变成确定性报告**。

**90. strace 怎么用？举例说明它纠正过的错误判断。**
`strace -f -T -e trace=fsync,write -p <pid>` 可以看每次系统调用的耗时。我们一度以为 fsync 是写瓶颈（"每次 9.3ms"），strace 实测只有 **0.34ms/次** —— 真正的瓶颈是 **fsync 的次数**（每条日志一次），这就直接指向了组提交方案。

**91. A/B 对照实验怎么设计才可信？**
只改一个变量，其余全部固定（同集群规模、同节点角色、同时长、同并发、同 key）；两组都要能重复出结论；并且要**确认改动真的生效**（我们为此在启动日志里打印生效参数）。例：冻结 follower 的同步 vs 异步发送、日志开 vs 关、tick 100 vs 10。

**92. RSS 怎么看内存泄漏？**
读 `/proc/<pid>/status` 的 `VmRSS`。判断泄漏要看**趋势**：持续压测下 RSS 单调上涨、停止后不回落，就是泄漏。实测 `Send` 泄漏未修时 40 秒涨 113MB，修复后同样的压测只涨 15MB（正常波动），空闲 2 分钟仅涨 48KB。

**93. 容器 CPU/内存限制怎么影响性能结论？**
本项目容器 4 CPU 且与宿主共享，节点 + 压测客户端严重超配，因此**绝对延迟被显著放大**（Get 单请求 86.7ms、强读平均 5.3s）。所以结论要讲**相对关系**（组提交 20 倍、共识/非共识 4~6 倍、FD 8800→26），不要把绝对数字当生产指标；跨环境复测是必须的。

**94. 怎么让性能结论可复现？**
① 把整套流程脚本化（`bench-suite.sh` / `leader-suite.sh` / `tick-experiment.sh`），一条命令跑完全部场景；② 参数全部可通过环境变量传入；③ 结果落成结构化表格（TSV/JSON）；④ 固定集群启动方式、线程数、时长、key；⑤ 重要结论至少跑两遍看波动。

**95. 单机三节点测出来的数字能代表生产吗？**
不能。单机三节点共享 CPU、内存带宽和网卡，既放大了干扰（调度抖动），也回避了真实网络 RTT、跨机时钟漂移、磁盘 IO 竞争。可以用它做**相对比较和回归**，生产容量必须多机复测。

**96. 如果要把写吞吐再提 10 倍，你会怎么做？**
按瓶颈顺序：① **Pipeline/batch 复制**（一次 RPC 发多条日志，减少往返）；② 把 fsync 换成组提交 + 更大批次，或对 WAL 用 **O_DIRECT/预分配**减少抖动；③ 让状态机应用与日志落盘**并行**（现在是串行）；④ 减少单次写入的字节量（`Entry` 里目前塞了完整 `RaftEntryData`，含 nodeid/requestid/key/value，可以精简）；⑤ 最根本的是**多 Raft group 分片**，把单组单线程的天花板拆掉。

**97. 要支持海量数据，架构怎么演进？**
单 Raft group 存不下也压不动，应引入**分片（multi-raft）**：按 key range 或 hash 切成多个 group，每个 group 独立选举与复制，再加一个元数据/路由层（也叫 placement driver）管理分片分布与迁移。同时配合 region 分裂/合并、Learner 节点做扩容时的追数据。

**98. 读多写少的场景怎么改？**
① 默认走 ReadIndex 或弱读（实测非共识路径吞吐是共识路径的 4~6 倍）；② 增加 follower 承担读流量（ReadIndex 天然支持 follower 读）；③ **批量读合并**（把多个 key 的读打包成一次 RPC）；④ 热点 key 加本地缓存（但要处理失效与一致性）；⑤ 读副本用 Learner。

**99. 怎么保证升级/重启不丢数据、不停服？**
滚动重启：一次只重启一个节点（3 节点最多容忍 1 个不可用），重启前先做 **leader 转移**避免服务抖动；节点退出走 SIGTERM 优雅路径（WAL fsync 落盘）；新进程靠 `ReplayWAL` + 快照恢复。验收标准：重启后 `appliedIndex` 与集群一致、无 FATAL、无数据丢失。

**100. 如果重新设计这个项目，你会改什么？**
① 把"读"从 raft 线程彻底解耦（当前读也占用共识线程）；② 用 **multi-raft 分片**打破单组天花板；③ 引入 pipeline 复制与真正的批量 RPC；④ pendingRequests 换成**无锁或分片表**，去掉全局互斥；⑤ 补齐可观测性（服务端耗时直方图、每阶段埋点），这样尾延迟能一次定位到具体阶段，而不用靠黑盒对照一层层排除；⑥ 把 ZK 依赖改成可选（客户端直连 + 节点转发或轻量元数据服务）。
